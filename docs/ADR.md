# Architecture Decision Records

## 철학
실습 프로젝트다. **작동하는 최소 구현**을 선택하고, 커머스에서 진짜 중요한 것 — 돈 계산과 권한 — 만 타협 없이 지킨다.
외부 의존성은 최소화하되, 직접 만들면 실습 시간이 다 날아가는 것(인증·DB)은 관리형 서비스에 맡긴다.

각 항목은 **결정 / 이유 / 트레이드오프** 순서다. 트레이드오프가 비어 있는 결정은 결정이 아니라 취향이다.

---

## 기반

### ADR-001: Next.js 15 App Router + Server Components 기본
**결정**: App Router를 쓰고, 데이터 조회는 Server Component에서 `services/` 함수를 직접 호출한다. 조회용 REST 라우트를 만들지 않는다. 변경은 Server Action으로 한다.
**이유**: 상품 목록/상세는 대부분 읽기다. 라우트 핸들러를 거치면 타입이 한 번 끊기고(직렬화), 캐시·로딩 상태를 손으로 관리해야 한다. Server Component에서 `await`하면 그 계층이 통째로 사라진다.
**트레이드오프**: 나중에 모바일 앱 같은 다른 클라이언트가 붙으면 API 계층을 새로 만들어야 한다. MVP 범위에서는 그럴 일이 없다고 보고 감수한다.

### ADR-002: 백엔드는 Supabase (Postgres + Auth + RLS)
**결정**: 자체 백엔드 서버나 ORM(Prisma 등) 없이 Supabase를 직접 쓴다. 권한은 애플리케이션 코드가 아니라 **DB의 RLS 정책**으로 표현한다.
**이유**: 인증·세션·권한을 직접 구현하면 실습의 대부분을 거기에 쓰게 된다. 그리고 브라우저에 나가는 anon 키는 공개값이므로, 어차피 **RLS가 유일한 신뢰 경계**다. 권한을 코드에 두면 `where` 하나를 빠뜨렸을 때 남의 데이터가 새지만, DB에 두면 코드가 틀려도 막힌다.
**트레이드오프**: 외부 서비스에 종속되고, SQL/RLS 문법을 새로 배워야 한다. 무료 티어는 일정 기간 미사용 시 프로젝트가 일시정지되므로 실습 재개 시 대시보드에서 되살려야 한다.

### ADR-003: 결제는 모의(mock) 처리
**결정**: 실제 PG를 붙이지 않는다. 체크아웃에서 "결제 승인"은 항상 성공하고, 주문 그룹을 `paid` 상태로 만드는 것으로 끝낸다.
**이유**: PG 연동은 사업자 등록·심사·웹훅 검증이 필요해 실습에서 진행이 막힌다. 주문/재고/가격 계산이라는 이 프로젝트의 핵심 로직은 결제 없이도 전부 연습된다.
**트레이드오프**: 실제 결제 실패·부분 취소·웹훅 멱등성 같은 현실의 어려운 부분은 다루지 못한다. 대신 주문 생성을 나중에 PG를 끼워 넣을 수 있는 형태(주문 먼저 생성 → 상태 전이)로 만들어 둔다.

### ADR-004: TDD는 `lib/`에만 적용
**결정**: `src/lib/`의 순수 함수는 테스트를 먼저 쓰고 통과시킨다. `services/`·`components/`·Server Action·라우트는 유닛 테스트 대신 `npm run build` 통과 + 개발 서버 수동 검증으로 대체한다.
**이유**: 커머스에서 버그가 돈이 되는 곳은 합계 계산·수량 병합·검증 같은 순수 로직이고, 이건 테스트가 싸고 확실하다. 반면 Supabase 래퍼를 테스트하려면 DB를 모킹해야 하는데, 그 모킹은 **실제 RLS 동작을 검증하지 못하면서** 유지보수 비용만 만든다.
**트레이드오프**: 서비스 계층의 회귀는 수동 검증에 의존한다. 대신 규칙을 RLS와 DB 제약(UNIQUE, CHECK, NOT NULL, 외래키)으로 내려서, 코드가 틀려도 DB가 막게 만든다.

## 돈

### ADR-005: 통화는 KRW 하나, 금액은 원 단위 정수로만 저장·계산
**결정**: 다중 통화를 지원하지 않는다. 모든 금액 컬럼은 `integer`(원 단위)이고 계산도 정수 연산만 한다. `numeric`/`float`/`Decimal` 금지.
**이유**: 부동소수 금액은 `0.1 + 0.2 !== 0.3` 류의 오차가 합계에 누적된다. 커머스에서 1원 차이는 버그다. KRW는 최소단위가 1원이라 정수만으로 손실 없이 표현된다.
**트레이드오프**: 나중에 USD처럼 소수 단위가 있는 통화를 붙이려면 컬럼을 최소단위(cents)로 재해석하고 마이그레이션해야 한다. MVP 범위에서 다중 통화는 필요 없다고 보고 감수한다. 표시는 `lib/pricing.ts`의 `formatPrice`로 한 곳에 모은다.

### ADR-006: 주문은 가격·상품명을 스냅샷으로 저장
**결정**: `order_items`에 `unit_price`, `name_snapshot`을 복사해 넣는다. 주문 조회 시 `products`를 조인해 현재 가격을 읽지 않는다. `order_items.product_id`는 `on delete set null`로 두어 상품이 삭제돼도 주문 기록이 남게 한다.
**이유**: 상품 가격이 바뀌거나 상품이 삭제돼도 과거 주문 금액은 절대 변하면 안 된다. 영수증이 소급 변경되는 셈이 된다. 정규화보다 이력 보존이 우선이다.
**트레이드오프**: 데이터가 중복된다. 의도된 비정규화다. `product_id`가 NULL이 될 수 있으므로 재고 복구 로직에서 NULL을 건너뛰어야 한다.

### ADR-012: 배송비는 판매자별로 계산한다
**결정**: 배송비 무료 임계값(50,000원)과 배송비(3,000원)를 **주문 전체가 아니라 판매자 그룹마다** 적용한다. 빈 그룹에는 배송비를 붙이지 않는다.
**이유**: 실제로 물건을 부치는 주체가 판매자다. 주문 전체 기준으로 하면 A에서 3만원, B에서 3만원 산 손님이 무료배송을 받는데, 두 판매자는 각각 3만원짜리 배송을 공짜로 하게 된다.
**트레이드오프**: 장바구니·체크아웃 화면이 판매자별로 쪼개져 복잡해지고, 손님이 배송비를 여러 번 내는 것처럼 보인다. 대신 `lib/pricing.ts`가 단순 합산이 아니라 그룹핑 함수가 되면서 TDD 대상으로서의 가치는 올라간다.

### ADR-015: 배송비 계산이 SQL과 TypeScript 두 곳에 존재하는 것을 수용한다
**결정**: 화면 표시용 계산은 `lib/pricing.ts`(TypeScript)에, 실제 주문에 저장되는 계산은 `create_order` RPC(SQL) 안에 둔다. 같은 규칙이 두 곳에 존재하는 것을 알면서 그대로 둔다. 임계값과 배송비는 양쪽에서 상수로 분리한다.
**이유**: 중복을 없애려면 장바구니 화면도 DB 함수를 호출해 금액을 받아와야 하는데, 그러면 `lib/pricing.ts`의 TDD 대상이 거의 사라진다. **TDD 실습이 이 프로젝트의 축 하나**(ADR-004)이므로, 그 축을 지우면서까지 중복을 없애지는 않는다.
**트레이드오프**: 한쪽 상수만 고치면 화면에 보인 금액과 실제 청구액이 달라진다. 이건 규율에 의존하는 방어이므로, 주문 step의 검증 절차에 "화면 표시 금액과 저장된 금액이 일치하는가"를 수동 확인 항목으로 넣어 잡는다.

## 마켓플레이스 구조

### ADR-009: 주문은 `orders` / `order_groups` / `order_items` 3단으로 나눈다
**결정**: 결제 단위는 `orders`, 판매자별 이행 단위는 `order_groups`, 품목은 `order_items`다. `status`는 `order_groups`에만 둔다.
**이유**: 한 번 결제해도 A 판매자는 오늘 보내고 B는 모레 보낸다. 주문 전체에 상태 하나를 붙이면 "일부만 발송됨" 같은 상태를 계속 만들어내야 하고, 결국 항목별 상태로 돌아오게 된다. 발송·취소의 실제 단위가 판매자 그룹이므로 처음부터 그렇게 나눈다.
**트레이드오프**: 테이블이 하나 늘고, 주문 조회가 3단 조인이 된다. 화면도 "주문 안에 그룹, 그룹 안에 품목" 구조로 그려야 해서 단일 판매자 쇼핑몰보다 복잡하다.

### ADR-010: `orders`에 총액과 상태를 저장하지 않는다
**결정**: `orders`에는 배송지와 주문 시각만 둔다. 주문 총액은 저장하지 않고 그룹들의 `subtotal + shipping_fee` 합으로 계산한다.
**이유**: 판매자는 발송을 위해 자기 그룹이 속한 주문의 **배송지를 읽어야 한다.** 그래서 `orders` SELECT가 판매자에게 열린다. 이때 총액이 그 행에 있으면 "이 손님이 다른 판매자에게서 얼마를 샀는지"가 새어 나간다. 그룹의 금액이 이미 스냅샷(ADR-006)이므로 합계는 결정적이고, 저장하지 않아도 값이 흔들리지 않는다.
**트레이드오프**: 총액을 볼 때마다 그룹을 모아 더해야 한다. 주문 목록에서 총액을 보여주려면 그룹까지 함께 읽어야 하므로 쿼리가 무거워진다. RLS 요구사항이 스키마를 결정한 사례다.

### ADR-011: `profiles`와 `seller_profiles`를 분리한다
**결정**: 역할(`role`)은 `profiles`에 두고 본인만 읽게 하며, 공개되어야 하는 스토어명은 `seller_profiles`에 따로 두고 누구나 읽게 한다.
**이유**: 상품 상세에 판매자명을 보여주려면 스토어명이 익명에게도 읽혀야 한다. 그런데 `role`까지 공개하면 전체 사용자와 권한을 열거할 수 있게 된다. **RLS는 행 단위라 "이 컬럼만 공개"가 불가능하므로**, 공개 컬럼을 테이블로 분리하는 것 외에 방법이 없다.
**트레이드오프**: 테이블이 하나 늘고, 판매자 가입 시 두 행을 만들어야 한다. Postgres 뷰(`security_invoker`)로 푸는 방법도 있지만, 실습에서는 테이블 분리가 읽고 이해하기 쉽다.

### ADR-008: 역할은 3종이고, 판매자 격리는 RLS가 보장한다
**결정**: `profiles.role`은 `'customer' | 'seller' | 'admin'`이다. 가입 시 판매자를 선택할 수 있지만 `admin`으로는 스스로 갈 수 없다(SQL로만 승격). 판매자 격리(`seller_id = auth.uid()`)와 관리자 권한을 RLS 정책에 박는다. 미들웨어의 경로 검사는 UI 편의일 뿐이다.
**이유**: 미들웨어는 Server Action 호출 경로를 보호하지 못한다. 실제 방어선은 DB에 있어야 한다. 그리고 마켓플레이스에서 판매자가 자기 상품만 수정할 수 있다는 것은 **UI 규칙이 아니라 데이터 규칙**이다 — 판매자 콘솔 쿼리에서 `where seller_id = ...`를 빠뜨려도 남의 데이터가 나오면 안 된다.
**트레이드오프**: 첫 관리자 계정과 관리자 승격은 SQL로 직접 해야 한다(가입 UI로 관리자를 만들 수 없다). 의도된 제약이다. 판매자 자가 가입을 허용했으므로 심사 없이 누구나 상품을 올릴 수 있는데, 이는 ADR-016에 따라 MVP 범위 밖으로 둔다.

### ADR-016: 운영자 전용 화면은 MVP에서 만들지 않는다
**결정**: `admin` 역할은 RLS에서 전체 조회 권한만 갖고, 화면은 판매자 콘솔을 그대로 재사용한다(admin이면 전체가 보인다). 판매자 승격·정산·수수료·판매자 심사는 만들지 않는다.
**이유**: 마켓플레이스로 가면서 step이 이미 늘었다. 관리자 화면까지 만들면 step이 11~12개가 되어 실습이 늘어진다. 이걸 빼면 판매자 콘솔 step 하나로 대체되어 순증이 1개로 억제된다.
**트레이드오프**: 판매자 승격을 매번 Supabase SQL Editor에서 해야 한다. 운영 관점의 화면(전체 매출, 판매자 관리)은 연습하지 못한다.

## 데이터를 안전하게 바꾸기

### ADR-013: 주문 생성과 취소는 Postgres 함수(RPC)로 내린다
**결정**: `create_order(...)`와 `cancel_order_group(...)`을 `security definer` Postgres 함수로 만들고, `services/`는 이 RPC를 호출만 한다. 애플리케이션 코드에서 여러 쿼리를 순서대로 날려 처리하지 않는다.
**이유**: 주문 생성은 `orders` + `order_groups` + `order_items` INSERT + 재고 차감 + 장바구니 비우기다. 중간에 실패하면 **재고와 주문이 어긋난 채로 남는다.** 이걸 앱 코드에서 보상 로직으로 되돌리려는 시도는 거의 항상 틀린다. 한 번의 RPC 호출은 통째로 하나의 트랜잭션이므로, 실패하면 전부 없던 일이 된다.
**트레이드오프**: 비즈니스 로직 일부가 TypeScript가 아니라 SQL로 쓰이게 되어, 읽는 사람이 두 언어를 오가야 한다. 마이그레이션 파일로 관리되므로 버전 관리는 되지만, 타입 검사와 테스트의 도움을 받지 못한다.

### ADR-014: 상태 변경은 조건부 UPDATE의 영향 행 수로 판정한다
**결정**: 재고 차감은 `update products set stock = stock - $n where id = $id and stock >= $n`, 취소는 `update order_groups set status='cancelled' where id = $1 and status = 'paid'`처럼 **조건을 걸고 바꾼다.** 영향 행이 0이면 실패로 처리한다. `select`로 확인한 뒤 `update`하는 방식을 금지한다.
**이유**: 확인과 변경이 두 동작으로 나뉘면 그 사이에 다른 요청이 끼어든다. 재고 1개짜리를 두 사람이 동시에 주문하면 둘 다 성공해 재고가 −1이 되고, 취소 버튼을 두 번 빠르게 누르면 재고가 두 배로 복구된다. 조건부 UPDATE는 확인과 변경이 한 동작이라 끼어들 틈이 없고, 그 자체로 **멱등**이다.
**트레이드오프**: 실패 사유를 세분화하기 어렵다. "영향 행 0"이 재고 부족인지 이미 취소된 것인지 구분하려면 추가 조회가 필요하다. 사용자 메시지를 위해 그 조회를 한 번 더 하는 것은 허용하되, **판정은 반드시 영향 행 수로 한다.**

## 사용자 경험

### ADR-007: 비로그인 장바구니는 localStorage, 로그인 시 서버로 병합
**결정**: 로그인하지 않은 사용자의 장바구니는 브라우저 `localStorage`에 둔다. 로그인하면 서버 장바구니와 병합(같은 상품은 수량 합산, 재고 상한으로 클램프, 품절·삭제 상품은 제외)하고 로컬을 비운다.
**이유**: 담기 위해 로그인부터 시키면 이탈한다. 반대로 비로그인 장바구니를 DB에 만들면 익명 세션과 고아 레코드 정리 문제가 따라온다.
**트레이드오프**: 병합 로직이 필요하고, 기기 간에 비로그인 장바구니가 공유되지 않는다. 병합 함수는 `lib/`의 순수 함수로 TDD한다.

### ADR-017: 취소는 판매자 그룹 단위이고, 구매자와 판매자 모두 할 수 있다
**결정**: 취소 단위는 주문 전체가 아니라 판매자 그룹이다. `paid` 상태인 그룹만 취소할 수 있고, 구매자 본인과 해당 그룹의 판매자가 각각 취소할 수 있다. 취소하면 그 그룹 품목의 재고가 복구된다. 그룹 안의 일부 상품만 취소하는 부분 취소는 만들지 않는다.
**이유**: 발송 주체가 판매자별로 다르므로 취소도 그 단위여야 한다. 구매자가 직접 취소하지 못하면 "판매자에게 연락해서 취소해달라고 하기"가 되어 실습에서 확인할 수 없는 흐름이 된다. 재고를 복구하지 않으면 취소할수록 팔 수 있는 물건이 사라지는데, 이건 기능이 아니라 그냥 버그다.
**트레이드오프**: 부분 취소를 빼서, 3개 중 1개만 취소하고 싶은 경우를 지원하지 못한다. 그리고 취소·복구가 생기면서 동시성 문제가 실제로 발생하는 지점이 하나 늘었다 — ADR-014가 그래서 필요하다.
