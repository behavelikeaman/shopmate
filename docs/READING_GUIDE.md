# 코드 읽는 순서

이 문서는 **코드를 처음 읽는 사람**이 어떤 순서로 봐야 전체가 이해되는지 안내한다.
낯선 단어가 나오면 [`docs/GLOSSARY.md`](GLOSSARY.md)를 먼저 본다.

---

## 시작 전에 — 파일 이름표

모든 파일 맨 위에 이런 이름표가 붙어 있다.

```
// ══════════════════════════════════════════════
// [계산기] 금액 계산
// 장바구니를 판매자별로 묶고, 소계·배송비·총액을 계산한다.
// ══════════════════════════════════════════════
```

| 이름표 | 무엇 | 어디 |
|---|---|---|
| `[화면]` | 손님이 보는 페이지 | `src/app/**/page.tsx` |
| `[부품]` | 화면을 이루는 조각 | `src/components/` |
| `[동작]` | 버튼을 누르면 **서버에서** 실행되는 코드 | `src/app/**/actions.ts` |
| `[계산기]` | 데이터베이스를 모르는 순수 계산 | `src/lib/` |
| `[시험]` | 계산기가 맞는지 자동 확인 | `src/lib/*.test.ts` |
| `[창구]` | 데이터베이스에 말을 거는 곳 | `src/services/` |
| `[설계도]` | 데이터 생김새 · 표 만들기 | `src/types/`, `0001_schema.sql` |
| `[규칙]` | 누가 무엇을 볼 수 있는지 | `0002_rls.sql` |
| `[금고]` | 주문·취소 처리 | `0004_order_rpc.sql` |
| `[문지기]` | 모든 요청이 거쳐가는 검문소 | `src/middleware.ts` |

**중요한 곳에는 `★` 표시가 있다.** 급하면 `★`만 따라 읽어도 된다.

## 1장 · 무엇을 왜 만들었나 (30분)

코드를 열기 전에 문서부터 본다. **코드는 "어떻게"만 말하고, "왜"는 문서에만 있다.**

| 순서 | 파일 | 무엇 |
|---|---|---|
| 1 | [`docs/PRD.md`](PRD.md) | 무엇을 만들기로 했나 |
| 2 | [`docs/ARCHITECTURE.md`](ARCHITECTURE.md) | 어떤 구조로 만들었나 |
| 3 | [`docs/ADR.md`](ADR.md) | 왜 그렇게 정했나 (17건) |

> **ADR을 꼭 보세요.** 나중에 코드를 보다가 "왜 이렇게 이상하게 했지?" 싶은 것들의 답이 전부 여기 있습니다.

## 2장 · 데이터가 어떻게 생겼나 (30분)

**모든 것의 출발점은 데이터다.** 화면도 계산도 결국 이 표들을 다루는 일이다.

### ① `supabase/migrations/0001_schema.sql` — 표 8개
```
회원      profiles, seller_profiles
상품      products
장바구니   carts, cart_items
주문      orders, order_groups, order_items
```

**주문이 왜 표 3개인지**만 이해하면 이 장은 끝이다.

```
orders          "누가, 어디로 받는가"          ← 결제 1번
  └ order_groups  "어느 판매자 몫인가"          ← 판매자마다 1개, 상태도 여기
      └ order_items  "무슨 상품 몇 개 얼마에"    ← 품목
```

한 번 결제해도 A 판매자는 오늘, B 판매자는 모레 보낸다. 그래서 상태가 하나일 수 없다.

### ② `src/types/index.ts` — 같은 것을 코드 쪽에서 본 모습

## 3장 · 권한 — ★ 가장 중요 (40분)

### `supabase/migrations/0002_rls.sql`

**이 파일 하나만 제대로 읽어도 이 프로젝트의 절반을 이해한 것이다.**

보통 쇼핑몰은 "내 주문만 보여주기"를 앱 코드로 한다. 조건 하나만 빠뜨리면 남의 주문이 다 보인다.
여기서는 그 규칙을 **데이터베이스에 못 박았다.** 코드가 틀려도 막힌다.

읽는 요령 — 표 하나씩, 이 질문에 답해본다:

| 표 | 질문 |
|---|---|
| `products` | 누가 볼 수 있나? 누가 고칠 수 있나? |
| `orders` | 판매자가 남의 배송지를 볼 수 있나? |
| `order_groups` | 취소는 누가 할 수 있나? |

### 여기서 만나는 가장 재미있는 부분

> **판매자는 발송하려면 배송지를 봐야 한다.**
> 그런데 배송지가 있는 표에 **총액도 같이 있으면**,
> "이 손님이 다른 판매자에게서 얼마 샀는지"가 새어 나간다.
>
> **그래서 총액 칸을 아예 없앴다.** 필요할 때 더해서 쓴다.

권한을 진지하게 그렸더니 **표 설계가 바뀐** 사례다. ([ADR-010](ADR.md))

## 4장 · 돈 계산 (30분)

### ① `src/lib/pricing.ts` + `pricing.test.ts`

**계산기부터 본다.** 데이터베이스를 모르는 순수한 계산이라 가장 읽기 쉽다.

시험 파일(`pricing.test.ts`)을 **먼저** 보는 것을 권한다. "이런 경우엔 이 답이 나와야 한다"가 나열돼 있어서, 규칙이 말로 적힌 것과 같다.

가장 중요한 시험 하나:

> 전체로는 6만원인데 A에서 3만원, B에서 3만원 샀다면?
> → **배송비가 양쪽 다 붙는다.** 실제로 물건을 부치는 건 판매자니까.

### ② `supabase/migrations/0004_order_rpc.sql` — ★ 주문의 심장

주문 한 번에 세 가지 일이 동시에 일어난다.

```
주문서 저장  →  재고 차감  →  장바구니 비우기
```

**중간에 하나라도 실패하면 전부 없던 일이 되어야 한다.** 그래서 데이터베이스 안에 넣었다.

여기서 꼭 볼 것 — **동시에 두 사람이 마지막 하나를 살 때:**

```sql
-- 위험한 방법
재고를 읽는다 → 충분한지 본다 → 뺀다
                ↑ 이 사이에 남이 끼어든다

-- 이 프로젝트의 방법
update products set stock = stock - 2
 where id = ... and stock >= 2
                    ↑ 확인과 빼기가 한 동작
```

취소도 같은 방식이다. 두 번 눌러도 재고는 한 번만 돌아간다.

> **여기까지 읽으면 이 프로젝트의 어려운 부분은 다 본 것이다.**
> 5장부터는 훨씬 쉽다.

## 5장 · 데이터베이스에 말 걸기 (30분)

`src/services/` — 화면과 데이터베이스 사이의 창구다.

| 순서 | 파일 | 볼 것 |
|---|---|---|
| 1 | `supabase.ts` | ★ 마스터 열쇠가 **이 파일에만** 있고, 어디서도 안 쓰인다 |
| 2 | `products.ts` | 상품 읽기. 상품 등록 시 '누가 파는지'를 서버가 채운다 |
| 3 | `auth.ts` | 판매자인지를 **데이터베이스에 다시 물어본다** |
| 4 | `cart.ts` | 계산은 안 한다. `lib/`의 계산기를 부른다 |
| 5 | `orders.ts` | ★ 주문 만드는 계산이 **없다.** 금고(4장)를 부르기만 한다 |

**5번이 이 장의 핵심이다.** 어려운 일은 전부 데이터베이스가 하고, 코드는 심부름만 한다.

## 6장 · 화면 (40분)

**손님이 실제로 거치는 순서대로** 따라간다.

| 순서 | 파일 | 화면 |
|---|---|---|
| 1 | `src/app/page.tsx` | 상품 목록 |
| 2 | `src/app/products/[id]/page.tsx` | 상품 상세 |
| 3 | `src/app/cart/page.tsx` | 장바구니 |
| 4 | `src/app/checkout/page.tsx` | 결제 |
| 5 | `src/app/orders/[id]/page.tsx` | 주문 상세 |

### 화면을 보면서 확인할 것 두 가지

**① 서버에서 만드는 화면 vs 브라우저에서 도는 화면**

맨 위에 `'use client'`가 있으면 브라우저에서 도는 것이다. 없으면 서버에서 만들어 완성본만 보낸다.

> 왜 나누나 → **서버는 비밀을 가질 수 있고 브라우저는 못 가진다.**
> 브라우저로 내려간 코드는 손님이 전부 열어볼 수 있다.

**② 판매자 묶음이 세 화면에서 똑같이 생겼다**

`src/components/SellerGroupBlock.tsx` 하나를 장바구니·결제·주문상세가 함께 쓴다. 그래서 어디서나 같은 모양이다.

## 7장 · 버튼을 누르면 (20분)

`actions.ts` 파일들 — 버튼을 누르면 **서버에서** 실행되는 코드다.

| 파일 | 볼 것 |
|---|---|
| `src/app/cart/actions.ts` | 브라우저가 보낸 수량을 안 믿고 재고를 다시 읽는다 |
| `src/app/checkout/actions.ts` | ★ **폼에서 금액을 받지 않는다.** 배송지 세 칸이 전부 |
| `src/app/seller/products/actions.ts` | ★ 각 동작마다 '판매자 맞나'를 **다시** 확인한다 |

### 관통하는 원칙 하나

> **브라우저에서 온 것은 아무것도 믿지 않는다.**
>
> 금액을 받으면 1원으로 바꿔 보낼 수 있다.
> 화면에서 버튼을 숨겨도 그 코드는 직접 부를 수 있다.

| 파일 | 볼 것 |
|---|---|
| `src/app/seller/layout.tsx` | 판매자 확인을 한 곳에 모았다 |

### ★ 직접 확인해볼 것

판매자 A로 로그인해서, 판매자 B의 상품 수정 주소로 직접 들어가 보라.

- **화면은 열린다** — 상품 정보는 원래 누구나 볼 수 있으니까
- **저장은 안 된다** — 데이터베이스가 막는다

화면을 막는 것과 데이터를 막는 것이 **다른 일**이라는 걸 몸으로 알 수 있다.

## 9장 · 이 프로젝트의 만드는 방식 (20분)

| 파일 | 무엇 |
|---|---|
| `CLAUDE.md` | AI가 지켜야 할 규칙 |
| `phases/0-mvp/step0.md` ~ `step9.md` | 10단계 작업 지시서 |
| `scripts/execute.py` | 지시서를 순서대로 실행하는 프로그램 |

`step0.md` 하나만 읽어봐도 방식이 보인다. 각 지시서에는 항상 이 네 가지가 있다:

```
읽어야 할 파일    → 맥락 없이 시작하지 않게
작업             → 무엇을 만들지
합격 기준         → 실행 가능한 명령어로 (추상적인 말 금지)
금지사항          → "X 하지 마라. 이유: Y" 형식으로
```

**핵심**: 각 단계는 **아무것도 모르는 새 세션**이 실행한다. 그래서 지시서에 "아까 말한 대로" 같은 표현을 쓸 수 없다. 필요한 걸 전부 파일에 적어야 한다.

# 이 프로젝트를 관통하는 생각 3개

읽다 보면 계속 마주치게 될 것들이다.

### ① 규칙은 코드가 아니라 데이터베이스에 둔다
코드는 실수한다. 조건 하나 빠뜨리면 남의 데이터가 새어 나간다.
데이터베이스에 못 박아 두면 코드가 틀려도 막힌다.

### ② 브라우저에서 온 것은 아무것도 믿지 않는다
금액도, 수량도, 누가 파는지도 서버가 다시 읽는다.
화면에서 버튼을 숨기는 것은 보안이 아니라 친절이다.

### ③ 확인하고 나서 바꾸지 말고, 조건을 걸고 바꾼다
"재고 있나 보고 → 빼기"는 그 사이에 남이 끼어든다.
"재고가 충분할 때만 빼기"는 끼어들 틈이 없다.
