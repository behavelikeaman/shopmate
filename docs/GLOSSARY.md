# 용어 사전 — ARCHITECTURE.md를 읽기 위한 배경 지식

이 문서는 코드를 쓰지 않는 사람이 `docs/ARCHITECTURE.md`와 `docs/ADR.md`를 읽을 수 있게 하려고 만들었다.
각 용어는 **한 줄 정의 → 풀어쓴 설명 → 우리 프로젝트에서의 쓰임** 순서로 적는다.

---

## 0. 큰 그림

손님이 상품 페이지를 열었을 때 벌어지는 일:

```
[브라우저]  "/products/abc 주세요"
     │
     ▼
[Next.js 서버]  페이지를 만들 코드를 실행한다
     │            ↳ services/products.ts 의 getProduct('abc') 호출
     ▼
[Supabase / Postgres]  products 테이블에서 abc 행을 찾는다
     │                   ↳ RLS가 "이 사람이 이 행을 봐도 되나" 검사
     ▼
[Next.js 서버]  받은 데이터로 HTML을 완성한다
     │
     ▼
[브라우저]  완성된 화면을 그린다
```

핵심은 **DB에 직접 말을 거는 쪽이 브라우저가 아니라 서버**라는 것, 그리고 **DB가 스스로 권한을 검사한다**는 것이다. 이 두 가지가 이 프로젝트 설계의 축이다.

## 1. 웹 앱의 뼈대

### Next.js
> 웹사이트를 만드는 도구 모음(프레임워크).

브라우저에 보이는 화면, 그 화면을 만들어내는 서버, 둘 사이를 오가는 통신을 한 덩어리로 묶어준다. 이게 없으면 화면용 프로그램과 서버용 프로그램을 따로 만들어 붙여야 한다.

**우리 프로젝트**: 버전 15를 쓴다. 상품 목록·장바구니·주문 화면이 전부 Next.js 위에 올라간다.

### App Router
> Next.js에서 "폴더 구조 = 웹사이트 주소 구조"로 만드는 방식.

`src/app/cart/page.tsx` 파일을 만들면 `사이트주소/cart` 페이지가 생긴다. 별도의 주소 설정 파일이 필요 없다.

**우리 프로젝트**: `ARCHITECTURE.md`의 디렉토리 구조 그림이 그대로 사이트 주소 목록이다. `app/seller/products/` → `/seller/products`.

### `[id]` (동적 경로)
> 주소의 일부가 값에 따라 바뀌는 자리.

상품이 1000개면 페이지를 1000개 만들 수 없다. `products/[id]/page.tsx` 하나를 만들어두면 `/products/A`, `/products/B` 모두 이 파일이 처리하고, `id` 자리에 들어온 값을 코드가 받아 쓴다.

**우리 프로젝트**: `products/[id]`(상품 상세), `orders/[id]`(주문 상세).

### TypeScript
> 자바스크립트에 "이 값은 숫자, 저 값은 글자" 같은 표시를 붙인 언어.

표시를 붙여두면, 실수로 가격 자리에 사람 이름을 넣는 코드는 **실행하기 전에** 에러로 걸린다. 쇼핑몰에서 이런 실수는 돈이 틀어지는 사고다.

**우리 프로젝트**: `strict mode`로 쓴다. 검사를 가장 빡빡하게 켠 설정이다.

### 타입(type)
> 값의 생김새를 미리 적어둔 설계도.

`Product = { 이름: 글자, 가격: 숫자, 재고: 숫자 }`처럼 적어두면, 이 설계도에 맞지 않는 데이터는 코드가 거부한다.

**우리 프로젝트**: `src/types/`에 모아둔다. `Product`, `CartLine`, `Order` 등.

### Tailwind CSS
> 화면 꾸미기(색·여백·크기)를 짧은 이름표로 하는 방식.

"글자를 회색으로, 아래 여백 16px"를 별도 디자인 파일에 쓰는 대신 `text-neutral-500 mb-4`처럼 화면 코드에 바로 붙인다. 디자인이 코드 옆에 붙어 있어 찾기 쉽다.

**우리 프로젝트**: `docs/UI_GUIDE.md`의 색상·버튼 표에 적힌 값들이 전부 Tailwind 이름표다.

### npm / `package.json` / `node_modules`
> 남이 만든 코드 꾸러미를 받아오는 도구 / 무엇을 받을지 적은 목록 / 실제로 받아진 파일들.

`package.json`은 장바구니 목록, `node_modules`는 배송된 물건이다. 물건은 용량이 커서 깃(git)에 올리지 않고, 목록만 올린다. 다른 PC에서는 목록을 보고 `npm install`로 다시 받는다.

**우리 프로젝트**: 그래서 `README.md`의 "다른 PC에서 시작하기"에 `npm install`이 들어 있다.

### 빌드(build) / 개발 서버(dev)
> 실제 서비스용으로 압축·최적화하는 작업 / 개발 중 즉시 확인용으로 띄우는 임시 서버.

`npm run dev`는 코드를 고치면 화면이 바로 바뀐다. `npm run build`는 배포용 결과물을 만들면서 **타입 오류를 전부 잡아낸다.**

**우리 프로젝트**: 서비스 계층은 유닛 테스트 대신 `npm run build` 통과로 검증한다 (ADR-004).

### ESLint (lint)
> 코드 작성 규칙 위반을 잡아내는 검사기.

문법은 맞지만 위험하거나 지저분한 패턴을 지적한다. 맞춤법 검사기에 가깝다.

**우리 프로젝트**: `npm run lint`. 각 step의 합격 기준에 들어 있다.

## 2. 코드가 어디서 도는가

이 절이 `ARCHITECTURE.md`의 "패턴"과 "데이터 흐름"을 이해하는 열쇠다.

### 서버 / 클라이언트
> 우리가 운영하는 컴퓨터 / 손님의 브라우저.

**서버는 비밀을 가질 수 있고, 클라이언트는 가질 수 없다.** 브라우저로 내려간 코드는 손님이 전부 열어볼 수 있다. 이것이 "API 키를 서버에서만 다룬다"는 규칙의 이유다.

### 렌더링(rendering)
> 데이터를 눈에 보이는 화면으로 바꾸는 일.

### Server Component
> 서버에서만 실행되고, 결과 화면만 브라우저로 보내는 화면 조각.

DB에 직접 말을 걸 수 있다. 코드 자체는 브라우저로 가지 않으므로 비밀 값을 써도 안전하다. 대신 버튼 클릭 같은 반응은 못 한다.

**우리 프로젝트**: 상품 목록·상세·주문 내역이 전부 이것. 기본값이다.

### Client Component
> 브라우저로 내려가서 실행되는 화면 조각.

클릭·입력·수량 조절처럼 사용자와 주고받는 일을 한다. 대신 **DB에 직접 못 붙고, 비밀 값을 쥘 수 없다.**

**우리 프로젝트**: 수량 스테퍼, 검색 입력창, 비로그인 장바구니.

### Server Action
> 브라우저의 버튼이 서버의 함수를 직접 부르게 해주는 장치.

원래는 "브라우저 → 주소로 요청 → 서버가 받아서 처리"라는 배선을 손으로 깔아야 했다. Server Action은 그 배선을 자동으로 만들어준다. 함수에 `"use server"`라고 표시만 하면 된다.

**중요**: 브라우저가 부르는 것이므로, **보내온 값은 절대 믿으면 안 된다.** 서버에서 다시 검사해야 한다.

**우리 프로젝트**: 장바구니 담기, 주문하기, 취소, 발송 처리, 상품 등록이 전부 Server Action.

### `revalidatePath`
> "이 페이지의 저장된 화면은 이제 낡았으니 다시 만들어라"고 알리는 명령.

Next.js는 속도를 위해 만들어둔 화면을 저장해 재사용한다. 장바구니에 담았는데 화면이 그대로면 안 되므로, 바뀐 뒤에 이걸 호출해 새로 만들게 한다.

### 라우트 핸들러 (API 라우트)
> 화면이 아니라 데이터만 주고받는 주소.

`app/api/` 아래에 만든다. 화면 없이 요청을 받아 응답만 돌려준다.

**우리 프로젝트**: 거의 안 쓴다. 조회는 Server Component가, 변경은 Server Action이 하기 때문에 **꼭 필요한 경우(로그인 콜백)에만** 만든다 (ADR-001).

### 미들웨어(middleware)
> 모든 요청이 페이지에 닿기 전에 먼저 거치는 검문소.

**우리 프로젝트**: 만료되어 가는 로그인 세션을 갱신한다. 이게 없으면 사용자가 갑자기 로그아웃된다. 판매자 페이지 접근 차단도 여기서 하지만, **이건 편의일 뿐 진짜 방어선은 RLS다.**

### localStorage
> 브라우저가 자기 안에 데이터를 저장해두는 작은 공간.

새로고침하거나 브라우저를 껐다 켜도 남는다. 다만 **그 브라우저 안에만** 남는다. 다른 기기에서는 안 보인다.

**우리 프로젝트**: 로그인하지 않은 손님의 장바구니를 여기 둔다 (ADR-007). 로그인하면 서버 장바구니와 합치고 비운다.

## 3. 데이터베이스

### Supabase
> 데이터베이스 + 로그인 기능 + 권한 시스템을 통째로 빌려주는 서비스.

DB 서버를 직접 사서 설치·관리하는 대신 웹에서 프로젝트를 만들면 끝난다. 로그인(회원가입·비밀번호·세션)도 만들어져 있다.

**우리 프로젝트**: 백엔드를 직접 만들지 않기로 한 이유가 이것이다 (ADR-002).

### PostgreSQL (Postgres)
> Supabase 안에서 실제로 데이터를 저장하는 데이터베이스 프로그램.

Supabase는 포장이고, 알맹이는 Postgres다. 그래서 Postgres 기능(트랜잭션·함수·제약조건)을 그대로 쓸 수 있다.

### SQL
> 데이터베이스에게 말을 거는 언어.

`select * from products where category = '의류'` = "products에서 카테고리가 의류인 것 전부 줘".

**우리 프로젝트**: `supabase/migrations/`의 `.sql` 파일들이 이 언어로 쓰여 있다.

### 테이블 / 행(row) / 컬럼(column)
> 엑셀 시트 / 한 줄 / 한 칸의 세로 항목.

`products` 테이블 = 상품 시트. 행 하나 = 상품 하나. 컬럼 = 이름·가격·재고 같은 항목.

### 기본키(primary key) / uuid
> 행을 하나로 식별하는 번호 / 겹치지 않게 자동 생성되는 긴 문자열 번호.

1, 2, 3처럼 순서대로 매기면 "우리 쇼핑몰에 상품이 몇 개인지" 남에게 노출된다. uuid(`a3f1...` 같은 형태)는 그런 정보를 흘리지 않는다.

### 외래키(foreign key)
> "이 값은 저 테이블의 어떤 행을 가리킨다"는 연결선.

`products.seller_id`가 `auth.users`를 가리킨다 = "이 상품의 주인은 이 사용자". DB가 이 연결을 검사해서, 존재하지 않는 사용자를 주인으로 넣는 것을 막는다.

### `on delete cascade` / `on delete set null`
> 가리키던 행이 지워졌을 때 따라서 지운다 / 연결만 끊고 남긴다.

**우리 프로젝트**: 회원 탈퇴 시 장바구니는 `cascade`(따라서 삭제). 하지만 `order_items.product_id`는 `set null` — **상품이 삭제돼도 주문 기록은 남아야 하기 때문이다** (ADR-006).

### UNIQUE 제약
> "이 조합은 중복될 수 없다"는 DB 차원의 규칙.

**우리 프로젝트**: `cart_items`에 `UNIQUE(cart_id, product_id)`. 같은 장바구니에 같은 상품이 두 줄로 들어가는 것을 DB가 막는다. 코드가 실수해도 데이터는 안 망가진다.

### CHECK 제약
> "이 값은 이 범위 안이어야 한다"는 DB 차원의 규칙.

**우리 프로젝트**: `price >= 0`, `stock >= 0`, `quantity > 0`, `status in ('paid','shipped','cancelled')`. 음수 가격이나 이상한 상태값이 저장되는 것을 원천 차단한다.

### 인덱스(index)
> 자주 찾는 항목의 색인. 책 뒤의 찾아보기.

없어도 동작하지만, 데이터가 많아지면 느려진다.

**우리 프로젝트**: `products(category)`, `order_groups(seller_id, status)` 등. 판매자가 자기 주문만 볼 때 쓰는 조건들이다.

### 마이그레이션(migration)
> DB 구조를 바꾸는 작업을 SQL 파일로 남긴 것.

Supabase 웹 화면에서 손으로 테이블을 만들면, **다른 PC나 새 프로젝트에서 똑같이 재현할 방법이 없다.** 파일로 남겨야 순서대로 다시 실행할 수 있다.

**우리 프로젝트**: `supabase/migrations/0001_schema.sql` 같은 파일들. `CLAUDE.md`에 "대시보드에서 직접 고치고 끝내지 말 것"이 규칙으로 들어 있는 이유다.

### 시드(seed)
> 실습·테스트용으로 미리 넣어두는 예시 데이터.

**우리 프로젝트**: 상품 12개 정도. 빈 쇼핑몰로는 화면을 확인할 수 없다.

## 4. 누가 무엇을 볼 수 있는가

이 절이 이 프로젝트에서 **가장 중요한 부분**이다.

### 인증(authentication) vs 인가(authorization)
> "당신이 누구인지 확인" vs "그 사람이 이걸 해도 되는지 확인".

로그인은 인증. "이 판매자가 남의 상품을 수정해도 되나"는 인가. 둘은 다른 문제다.

### 세션(session) / 쿠키(cookie)
> 로그인 상태가 유지되는 기간 / 그 상태를 담아 브라우저에 보관하는 작은 표.

매 페이지마다 비밀번호를 다시 묻지 않는 이유가 이 표 덕분이다. 표에는 유효기간이 있어서 주기적으로 갱신해야 한다(그래서 미들웨어가 있다).

### anon 키 (`NEXT_PUBLIC_SUPABASE_ANON_KEY`)
> 브라우저에 공개되는 Supabase 접속 열쇠.

이름에 `PUBLIC`이 붙은 이유는 **숨길 수 없기 때문**이다. 손님이 브라우저 개발자 도구를 열면 그냥 보인다. 그래서 이 열쇠는 그 자체로는 아무 권한이 없고, **권한은 전부 RLS가 결정한다.**

### service_role 키
> RLS를 무시하고 DB 전체를 읽고 쓸 수 있는 마스터 열쇠.

유출되면 끝이다. 주문·회원 정보 전부 열린다.

**우리 프로젝트**: `CLAUDE.md`의 최상위 규칙 — 서버에서만, `services/` 안에서만. 이름에 `NEXT_PUBLIC_`을 붙이는 순간 브라우저로 새어 나간다.

### RLS (Row Level Security, 행 수준 보안)
> **데이터베이스가 스스로 "이 사람이 이 행을 봐도 되는지" 검사하는 기능.**

보통 웹 서비스는 "내 주문만 보여주기"를 코드에서 처리한다. `where user_id = 나`를 빼먹으면 남의 주문이 다 보인다. 실제로 이런 사고가 자주 난다.

RLS는 이 규칙을 **DB에 못 박는다.** 코드가 `where`를 빼먹어도 DB가 알아서 남의 행을 걸러낸다.

**우리 프로젝트**: anon 키가 공개값이므로 **RLS가 유일한 방어선**이다. `ARCHITECTURE.md`의 "권한(RLS)" 표가 그 방어선의 설계도다.

### 정책(policy)
> RLS의 개별 규칙 한 줄.

"`orders`는 `user_id`가 나인 행만 SELECT 가능" 같은 문장을 SQL로 쓴 것. 테이블마다 여러 개를 붙인다.

**주의**: RLS를 켜고 정책을 하나도 안 만들면 **아무도 아무것도 못 읽는다.** 켜는 것과 규칙을 쓰는 것은 별개 작업이다.

### `auth.uid()`
> "지금 요청을 보낸 사람의 ID"를 알려주는 DB 함수.

정책 안에서 `user_id = auth.uid()`처럼 쓴다. 이 값은 로그인 토큰에서 나오므로 손님이 위조할 수 없다.

### `security definer`
> "이 함수는 부른 사람 권한이 아니라, 만든 사람 권한으로 실행하라"는 표시.

**왜 필요한가**: `profiles` 테이블의 정책 안에서 "이 사람이 admin인가?"를 알려면 `profiles`를 다시 읽어야 한다. 그런데 그 읽기가 또 정책 검사를 부르고, 그게 또... 무한 반복에 빠진다. `security definer` 함수로 감싸면 이 고리가 끊긴다.

**우리 프로젝트**: `is_admin()` 헬퍼와 주문 생성·취소 RPC가 이것으로 만들어진다.

### 신뢰 경계(trust boundary)
> "여기서부터는 못 믿는다"는 선.

우리 프로젝트에서 그 선은 **DB 앞**에 있다. 브라우저에서 온 것은 물론이고, 서버 코드가 보낸 것조차 RLS가 다시 검사한다.

## 5. 데이터를 안전하게 바꾸기

주문 생성과 취소는 여러 테이블을 동시에 건드린다. 그래서 이 절의 개념이 필요하다.

### 트랜잭션(transaction)
> 여러 작업을 "전부 성공하거나, 전부 없던 일이 되거나" 둘 중 하나로 묶는 것.

주문 = 주문 기록 저장 + 재고 차감 + 장바구니 비우기. 재고를 깎다가 실패했는데 주문은 이미 저장됐다면, **재고와 주문이 어긋난 채로 남는다.** 트랜잭션으로 묶으면 실패 시 전부 원래대로 돌아간다.

### RPC (Postgres 함수)
> 여러 SQL 작업을 하나의 이름으로 묶어 DB 안에 저장해둔 것.

앱에서 쿼리를 다섯 번 날리면 그 사이사이가 위험하다. 다섯 개를 DB 안의 함수 하나로 만들어 두면, **한 번의 호출이 통째로 트랜잭션**이 된다.

**우리 프로젝트**: `create_order`(주문 생성), `cancel_order_group`(취소·재고 복구). ARCHITECTURE에서 이 둘을 필수로 정했다.

### 경쟁 상태(race condition)
> 두 요청이 동시에 들어와서 서로를 덮어쓰는 상황.

재고 1개짜리 상품을 두 사람이 동시에 주문한다. 둘 다 "재고 1개 있네" 확인하고, 둘 다 차감한다 → **재고가 -1이 되고 둘 다 주문에 성공한다.**

취소도 마찬가지다. 취소 버튼을 두 번 빠르게 누르면 재고가 두 배로 복구될 수 있다.

### 조건부 UPDATE
> 위 문제를 막는 방법. "확인한 뒤 바꾸기"가 아니라 "조건을 걸고 바꾸기".

```
(위험) 재고를 읽는다 → 충분한지 확인한다 → 차감한다
(안전) update products set stock = stock - 2 where id = X and stock >= 2
```
안전한 쪽은 확인과 변경이 **한 동작**이라 사이에 끼어들 틈이 없다. 조건이 안 맞으면 **바뀐 행이 0개**로 나오고, 그걸로 실패를 판정한다.

**우리 프로젝트**: 재고 차감과 취소 양쪽에 이 방식을 못 박았다.

### 멱등성(idempotency)
> 같은 요청을 여러 번 해도 결과가 한 번 한 것과 같은 성질.

취소 버튼을 세 번 눌러도 재고는 한 번만 복구되어야 한다. 조건부 UPDATE(`where status = 'paid'`)가 이걸 보장한다 — 첫 번째만 성공하고 나머지는 "바뀐 행 0개"가 된다.

### 스냅샷(snapshot)
> 그 시점의 값을 복사해서 따로 저장해두는 것.

주문 내역에서 상품 가격을 매번 `products` 테이블에서 읽어오면, **판매자가 가격을 바꾸는 순간 과거 주문 금액도 같이 바뀐다.** 영수증이 소급 변경되는 셈이다.

**우리 프로젝트**: `order_items`에 주문 당시의 상품명과 단가를 복사해 넣는다 (ADR-006).

### 비정규화(denormalization)
> 같은 데이터를 일부러 두 군데 저장하는 것.

보통은 피해야 할 일이지만, 스냅샷처럼 **"과거를 보존해야 하는 경우"는 의도적으로 한다.**

### 정수 금액
> 금액을 소수점 없이 정수로만 다루는 규칙.

컴퓨터는 소수 계산에 미세한 오차가 있다(`0.1 + 0.2`가 정확히 `0.3`이 아니다). 이 오차가 합계에 쌓이면 1원씩 틀어진다. 커머스에서 1원 차이는 버그다.

**우리 프로젝트**: 원 단위 정수만 쓴다 (ADR-005). 통화는 KRW 하나뿐이라 가능한 선택이다.

## 6. 만드는 방식

### 순수 함수(pure function)
> 같은 값을 넣으면 항상 같은 값이 나오고, 바깥 세상을 건드리지 않는 함수.

DB도 안 읽고, 파일도 안 쓰고, 시계도 안 본다. 입력 → 출력이 전부다. **그래서 테스트하기가 아주 쉽다.**

**우리 프로젝트**: `src/lib/`가 전부 이것. 합계 계산, 장바구니 병합, 입력 검증.

### TDD (테스트 주도 개발)
> 코드를 쓰기 전에 테스트부터 쓰는 방식.

"5만원어치 담으면 배송비가 0원이어야 한다"는 테스트를 먼저 쓴다 → 당연히 실패한다 → 통과하도록 코드를 쓴다. 순서를 뒤집으면 "이미 짠 코드에 맞춘 테스트"가 되어 버그를 못 잡는다.

**우리 프로젝트**: `lib/`에만 적용한다. 나머지는 빌드 통과 + 수동 확인으로 대체한다 (ADR-004). 전부 다 TDD 하면 실습 시간이 다 날아간다.

### 테스트 / vitest
> 코드가 의도대로 동작하는지 자동으로 확인하는 코드 / 그걸 실행해주는 도구.

`npm run test`로 돌린다. 나중에 다른 곳을 고쳤을 때 **예전 기능이 망가졌는지 자동으로 알려주는 것**이 진짜 가치다.

### 하네스(harness) / step / phase
> 큰 작업을 잘게 쪼개 순서대로 자동 실행시키는 이 프로젝트의 작업 방식.

`phases/0-mvp/step0.md` 같은 파일 하나가 "한 번의 작업 지시서"다. `scripts/execute.py`가 이 지시서를 순서대로 AI에게 넘기고, 실패하면 다시 시키고, 성공하면 커밋한다.

**핵심**: 각 step은 **독립된 세션**에서 실행된다. 그래서 지시서에 "아까 말한 대로" 같은 표현을 쓰면 안 되고, 필요한 정보를 전부 파일 안에 적어야 한다.

### 커밋(commit) / 브랜치(branch) / 푸시(push)
> 변경 사항을 기록으로 남기기 / 작업 갈래 / 그 기록을 GitHub에 올리기.

**우리 프로젝트**: 진행 상태(`phases/**/index.json`)까지 커밋하기 때문에, 푸시해두면 **다른 PC에서 받아서 그 다음 step부터 이어서** 할 수 있다.
